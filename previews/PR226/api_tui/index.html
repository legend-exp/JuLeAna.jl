Terminal interface

The types and functions behind the pages of the terminal user interface that JuLeAna.run_tui opens.

JuLeAna.JuLeAnaTUI — Type
mutable struct JuLeAnaTUI <: Tachikoma.Model

State of the terminal user interface opened by JuLeAna.run_tui.

JuLeAnaTUI(ctrl::DataflowController, messages::MessageBuffer = MessageBuffer()) shows the dataflow of ctrl. Controller commands run one after another in a background task, in the order they were sent, and state reads run in background tasks of the interface's Tachikoma.TaskQueue, so the interface never waits for the controller; the latest state read from it is kept in the fields snap, progress, busy and step_msgs (the messages of the step open on the Progress page, with the step's key).

A left click on a page's tab opens the page; other mouse events go to the visible page.

Keys: the visible page gets each key first (see JuLeAna.setup_key! for the Setup page, JuLeAna.graph_key! for the Graph page, JuLeAna.progress_key! for the Progress page and JuLeAna.log_key! for the Log page, JuLeAna.reports_key! for the Reports page and JuLeAna.history_key! for the History page and JuLeAna.workers_key! for the Workers page); otherwise 1 to 7 switch pages and q or Ctrl-C quits. While processing runs, quitting asks first: s stops processing after the running items and quits when the run has ended, q quits at once, ending the run and the workers connected to this process, and c or Escape keeps the interface open.

JuLeAnaTUI(ctrl, messages; splash_seconds = 1.5) shows a startup screen with the logo, the version and the link to the documentation in place of the page when the interface starts, until the session has loaded (or loading failed) and splash_seconds have passed; any key ends it and is not passed on. ? opens a panel that lists the keys of the visible page; Escape, ? or q closes it. The Setup page's filter and the kwargs editor receive ? as text.

N on the Setup page opens the JuLeAna.ProductionForm for a new data production. The form replaces the visible page and takes every key (see JuLeAna.production_key!). It is also open when the interface starts without a session: when the parsed options have no config or new_production is set, start! does not load a session.

The field timing is the JuLeAna.InterfaceTiming that records the times of the view and Tachikoma.update! calls; once a session is loaded it appends a row every 10 seconds to interface_timing.tsv in the log folder.

JuLeAna.MessageBuffer — Type
MessageBuffer(capacity::Integer = 1000; worker_capacity::Integer = 200)

Logger that keeps the last capacity lines of log messages and of captured terminal output as text, for the terminal user interface. Each line has the log level of its message and the number of its record: the lines of one log message share a record, each line of captured output is a record of its own. Output lines containing Warning: or Error: get the level Warn or Error, other output lines Info. Records below Info and progress bar records of ProgressLogging are dropped. A message that is not a string but can be shown as Markdown, such as a processor's report, is kept as that Markdown if it has at most 20 lines, else as one line with its section heading, processor status and length. A log message of a processing step (inside the step's scope set by run_processing) is also kept with the step in its ProgressStore (see step_messages). The newest warning or error, from a log record or from an output line containing Warning: or Error:, is kept as the alert of the buffer.

Output lines that Distributed relays from a worker (From worker <pid>:) are kept apart, the last worker_capacity lines per worker without the prefix, so that the output of many workers does not push out the other lines. Of the progress lines of @debug_progress, only the newest one of each description is kept. Relayed lines containing Warning: or Error: are also kept with the other lines.

JuLeAna.message_lines returns the kept lines as text, JuLeAna.message_entries with their levels and records, and JuLeAna.worker_output the lines of a worker.

JuLeAna.Checklist — Type
Checklist(entries; title = "", checked = (), focused = true, tag_style = tag -> nothing)

Terminal widget that displays a list of items with checkboxes and lets the user select any number of them.

entries is either a vector of JuLeAna.ChecklistItem (flat list) or a vector of JuLeAna.ChecklistGroup (two-level list). Item keys must be unique; checked is an iterable of the keys of the initially selected items and must only contain keys of items of the checklist. Only items are selected, never groups. The cursor row is highlighted only while focused is true. tag_style(tag::String) returns the Tachikoma.Style of a tag, or nothing for the dimmed default.

Selected boxes are drawn in the success color and group labels in bold primary color. A group row shows [x] if all of its visible items are selected, [~] if some are, and [ ] if none are. The title shows the number of selected items out of all items.

Keys

Tachikoma.handle_key!(w, evt) returns true if the widget used the key and false otherwise.

In normal mode:

  • Up, Down, PageUp, PageDown, Home, End move the cursor.
  • Space toggles the item under the cursor. On a group row it toggles all visible items of the group: if all are selected they are deselected, otherwise all are selected.
  • a selects and n deselects all visible items.
  • Left collapses the group under the cursor (the cursor moves to the group row if it is on one of its items), Right expands it, and Enter on a group row toggles it.
  • / starts editing the filter.
  • Escape clears a non-empty filter.
  • Other keys are not used.

While editing the filter, every key is used: printable characters are appended, Backspace deletes the last character, Enter keeps the filter and returns to normal mode, and Escape clears the filter and returns to normal mode.

The filter keeps the items whose label or any tag contains the filter text, ignoring case. A group is shown with all its items if its own label or a tag matches, and with only its matching items if just some of its items match. Visible items are the items shown under the filter, whether or not their group is collapsed.

Mouse

Tachikoma.handle_mouse!(w, evt) handles clicks and the scroll wheel using the area of the last Tachikoma.render(::JuLeAna.Checklist, ...).

JuLeAna.setup_key! — Function
JuLeAna.setup_key!(page::SetupPage, evt::Tachikoma.KeyEvent, snap, send)

Handle the key evt on the Setup page and return whether it was used. snap is the latest controller snapshot (or nothing) and send(cmd) sends a controller command.

An open kwargs or run mode editor gets every key (see JuLeAna.kwargs_key! and JuLeAna.runmode_key!); while writing the config waits for confirmation, y sends WriteConfig for the config folder of the data production and any other key cancels. An open picker gets every key: Up and Down move the cursor, Enter sends SelectProduction or SelectDataset for the chosen name unless it is the current one, and Escape closes the picker. While the production root is edited every key goes to its text (see JuLeAna.root_key!). Otherwise the focused checklist gets the key first; a change of its selection sends SelectRuns or SelectSteps. Then: Tab and Shift-Tab move between the panes; in a processor pane c and p select the cal and phy processors of the pane, d adds the steps the selected steps wait for and e opens the kwargs editor for the processor under the cursor; in the options pane Up and Down choose a row, Space or Enter cycles its value and e on the Run mode row opens the editor of the settings of the run modes; in the production pane Up and Down choose the root, the production or the dataset, Space or Enter edits the root in place or opens the picker of the production or dataset once the names are read; s starts processing, x stops it after the running items, X stops it without waiting for them, r reloads the config, g rebuilds the dependency graph, W starts a worker allocation with AddWorkers and w asks to write the current settings to config/processing_config.yaml of the data production. N sets page.new_production, which asks the interface to open the new-production form (see JuLeAna.ProductionForm); the checklists use n to uncheck all items.

JuLeAna.ProgressPage — Type
ProgressPage()

State of the Progress page of the terminal user interface: the row under the cursor, the first displayed row, whether the cursor follows the running step, and which groups the user folded or unfolded. The page lists the steps of the current or last processing run grouped by period and run, with the busy workers below. Keys are handled by JuLeAna.progress_key! and JuLeAna.progress_mouse!, the page is drawn by JuLeAna.render_progress.

A row is identified by its key: (period, run) for a group and (period, run, step) for a step, so that the cursor stays on its row when the list changes. expanded holds the group keys the user folded (false) or unfolded (true); the other groups are unfolded if a step runs, failed or stopped, or has items that were not run.

open is the key of the step whose messages pane is shown (nothing if closed). The pane lists the messages that step_messages returns for that step; while pane_follow is true it shows the newest lines, else it starts at line pane_top. While the pane is open, the cursor moving to another step row switches the pane to that step.

source
JuLeAna.progress_key! — Function
JuLeAna.progress_key!(page::ProgressPage, evt::Tachikoma.KeyEvent, prog)::Bool

Apply the key event evt to page for the progress prog (as returned by progress, or nothing). Return true if the key was used and false otherwise.

  • Up, Down, PageUp, PageDown, Home and End move the cursor and turn following off.
  • Enter on a group row toggles the group. Left folds the group of the cursor row and Right unfolds it. Folding a group moves the cursor to the group row. These keys turn following off.
  • Enter on a step row opens the messages pane for the step and turns following off; Enter on the open step's row closes the pane. Escape closes the pane.
  • While the pane is open, PageUp and PageDown scroll it instead of moving the cursor and End shows the newest line. Moving the cursor to another step row switches the pane to that step.
  • f turns following on: the cursor goes to the first running step and the view scrolls to keep it visible. An open pane follows the cursor's step.
  • Other keys are not used.

JuLeAna.render_progress(page::ProgressPage, prog, busy, msgs, area::Tachikoma.Rect, buf::Tachikoma.Buffer)

JuLeAna.GraphPage — Type
GraphPage()

State of the Graph page of the terminal user interface: the processor under the cursor, the first displayed row, whether unselected processors are shown, and the ProcessorGraph of the processors of the latest snapshot. JuLeAna.render_graph — Function
JuLeAna.render_graph(page::GraphPage, snap, prog, area::Tachikoma.Rect, buf::Tachikoma.Buffer; grid = nothing)

Draw the Graph page into area of buf from the controller snapshot snap, the progress prog (as returned by progress, or nothing) and the grid of the reports and the processing history grid (as returned by JuLeAna.history_grid, or nothing while it is not read).

Run-level processors are in the left lane and partition-level processors in the right lane, one row per processor in topological order, labeled with its display_name and category. A processor shows [x] if it is a selected step, else [ ], and the icon of its state in the last run: running, failed, done, or stopped. While page.disk is true the icon is instead the JuLeAna.disk_state of the processor over the selected periods and runs of snap: ✗ failed, – missing, ! warning or ✓ ok, and the last line also shows the counts of the processor under the cursor. The processor under the cursor is bold; the processors it requires are yellow and the processors that require it are purple, as are the edges between them. The view scrolls to keep the cursor row visible, and the last line shows the number of required and requiring processors and the tags of the processor under the cursor. Names are cut with … if the area is too narrow.

JuLeAna.ReportsPage — Type
ReportsPage()

State of the Reports page of the terminal user interface: the reports grouped by processor, the processing history, the row under the cursor, which groups the user folded or unfolded, the open report and the requests for reading the file system. The page lists all reports on disk (source is :all, report_overview), which it starts with, or the reports of the steps of the current or last processing run (:run, rows of report_index), and the failures of the processor under the cursor. A row is identified by its key, (group,) for a group and (group, period, run) for a report, where group is (name, level, category), so that the cursor stays on its row when the list is read anew. expanded holds the group keys the user folded (false) or unfolded (true); the other groups are unfolded if one of their reports failed.

JuLeAna.InterfaceTiming — Type
JuLeAna.InterfaceTiming(; window_seconds = 10, clock = time_ns, utc = () -> now(UTC), capacity = 8192, pages = 16)

Recorder of how responsive the terminal interface is, one window of window_seconds at a time. It keeps, in fixed-size buffers of capacity entries per kind of measurement (measurements beyond that are counted but not stored):

  • the interval between the starts of consecutive view calls (frame gaps),
  • the time spent in each view call and in each Tachikoma.update! call, with the maximum per event kind (key, mouse, task) and the kind or task id of the slowest call,
  • per page 1:pages, the number of view calls and the time spent in them, and the page of the slowest view call,
  • the key-to-redraw latency: from the start of the update! call for a key press to the end of the next view call. It does not include the time a key waited in the terminal input before the application loop read it; that shows up as a long frame gap,
  • the number of garbage collections, the time spent in them and the longest pause, from Base.gc_num(),
  • the thread and thread pool of the first view call.

The functions JuLeAna.timing_view_begin!, JuLeAna.timing_view_end!, JuLeAna.timing_update_begin! and JuLeAna.timing_update_end! feed the recorder; each takes one time reading and writes into the buffers without allocating. JuLeAna.timing_flush! closes the window.

clock returns the time in nanoseconds and utc the wall-clock time of a row; both can be replaced to feed synthetic times.

JuLeAna.TIMING_COLUMNS

Column names of the file interface_timing.tsv, in order: UTC time of the end of the window, controller state, number of frames, frame gap median, 95th percentile and maximum, view time 95th percentile and maximum, update! time 95th percentile and maximum, number of key presses, key-to-redraw latency median, 95th percentile and maximum, garbage collections in the window (count, time, longest pause), the longest update! for key, mouse and task events, the event kind or task id of the slowest update!, the length of the window in seconds, threadid:threadpool of the thread that draws, the page shown during the slowest view and, for each page shown, page:frames:mean view time separated by spaces. Times are in milliseconds; NA marks a statistic without measurements.

JuLeAna.timing_flush! — Function
JuLeAna.timing_flush!(t::InterfaceTiming, state, log_path)

Close the window of t: format its statistics as one tab-separated row (see JuLeAna.TIMING_COLUMNS for the columns), start a new window and return the row. state is the state of the controller. If log_path is a folder name, the row is appended to interface_timing.tsv in it by a separate task, preceded by the header if the file does not exist; the caller never waits for the file. With log_path = nothing or "" nothing is written.

Frame gaps, view times and update! times are in milliseconds. The garbage collector counts and time are those of the window. gc_max_pause_ms is the longest pause of the window if it exceeds all earlier pauses of the process, else an upper bound: the lesser of the longest earlier pause and the time spent in garbage collection in the window.
