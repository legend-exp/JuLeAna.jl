JuLeAna — Module
module JuLeAna

The Julia LEGEND Analysis dataflow.

JuLeAna.main is the entry point of the juleana app: it opens the terminal user interface (JuLeAna.run_tui) or, with --no-tui, runs the enabled processors with run_processing. JuLeAna.setup_session reads the processing config (ProcessingConfig), starts the workers, and returns a DataflowSession, which the DataflowController of the interface works on. The processors are the functions in src/processors/, registered by name in JuLeAna.PROCESSORS. The module also provides the helpers processors share: distributing work over the worker pool with per-item failure logging (parallel), combining per-item log rows into a processor status (master_status), report text and formatting helpers, and the Markdown-safe logger installed on the head and all workers.

JuLeAna.main — Function
main(args::AbstractVector{<:AbstractString})

Entry point of the juleana app and of julia -m JuLeAna: parse the command line options args (see juleana --help) and return the process exit code.

With --no-tui, run all enabled steps with run_no_tui and return its exit code. Otherwise open the terminal user interface with run_tui.

Install the app with Pkg.Apps.add(path = "<path to JuLeAna.jl>"); the juleana command then starts Julia with --threads=8,1, --gcthreads=8,1 and without the user's startup.jl (--startup-file=no): packages loaded there are not in the app's environment. Julia options placed before a -- replace these defaults, e.g. juleana --threads=16,1 -- -c config.json.

JuLeAna.setup_session — Function
setup_session(args::AbstractVector{<:AbstractString})
setup_session(parsed_args::AbstractDict; console::Bool = true, start_workers::Bool = true)

Set up a dataflow session from the command line options args (see juleana --help) or from their parsed form, as returned by parse_commandline.

Build the processing config and LegendData(:l200), run init_process on this process and register it for every worker, so that every process logs to its file in the config's log directory at the config's log_level (console = false turns off the terminal output of this process), and with start_workers start the workers of the configured run mode: local workers are always started; slurm workers only with submit_jobs, otherwise startjlworkers.sh is written to the JuLeAna.production_config_dir for manual submission. Without start_workers the worker pool starts empty. Then check the processor keyword arguments with check_processor_kwargs and build the dependency graph for the enabled steps.

Return the DataflowSession, ready for run_processing. Return nothing when args asks for --help or --version in an interactive session.

Examples

using JuLeAna
session = JuLeAna.setup_session(["--config", "config/processing_config.yaml", "--periods", "3"])
run_processing(session)

JuLeAna.run_no_tui — Function
run_no_tui(parsed_args::AbstractDict; processors = PROCESSORS, loader = setup_session,
    interval = 1, record_software = true, record_metadata = true)

Run all enabled processors of the session described by the parsed command line options parsed_args without the terminal user interface and return the process exit code.

Set up the session with loader(parsed_args) (by default setup_session, which also starts the workers and the log files), start processing through a DataflowController and show the progress bars of show_progress, updated every interval seconds, until the run ends. The first Ctrl-C stops the run after the running items, a second one stops it without waiting for them (see StopProcessing). Finally log a summary with the outcome, the duration, the number of steps per state and the failed and cancelled steps. With record_software and record_metadata, the run first records the software and the metadata in the production (see DataflowController).

The exit code is 0 when the run finished, 1 when it failed or the session could not be set up, and 2 when it was stopped.

JuLeAna.run_tui — Function
JuLeAna.run_tui(parsed_args::AbstractDict; processors = PROCESSORS, loader)

Open the terminal user interface with the pages Setup, Graph, Workers, Progress, Log, Reports and History on a DataflowController for the parsed command line options parsed_args, as returned by JuLeAna.parse_commandline. Returns nothing when the user quits.

The interface opens at once and loads the session in the background with loader(parsed_args). The default loader is setup_session without terminal output and without starting workers: it reads the config and the LEGEND data and builds the dependency graph. Log messages of this process and the output of its workers are kept in a JuLeAna.MessageBuffer instead of being printed; the newest warning or error is shown in the status panel, and the error of a failed load stays there. This process also writes its log file as in setup_session, and appends its captured error output to head-stderr.log in the log directory of the loaded session (see JuLeAna.MessageBuffer). The previous global logger is restored when the interface closes, and every worker allocation started from the interface is cancelled (see CancelAll). A startup screen with the logo is shown until the session has loaded; ? lists the keys of the visible page. See JuLeAna.JuLeAnaTUI for the keys. The log file records the thread setup (Interface threads) after the session has loaded.

JuLeAna.parse_commandline — Function
parse_commandline(args::AbstractVector{<:AbstractString})

Parse the command line options of the dataflow driver and return them as a Dict{String,Any} keyed by the long option names. With --help or --version, ArgParse prints the text and exits the process in a non-interactive session; in an interactive session it returns nothing.

Options (see juleana --help for the full text):

  • --config, -c: path of the processing config file. Without it, the JuLeAna.install_default_config file of the data production is used (copied from the config shipped with JuLeAna if the production has none), or nothing when LEGEND_DATA_CONFIG is not set (no data production is selected).
  • --periods, -p: periods, each optionally with runs: 6 (all runs of p06), 6,1 (r001), 6,1-3 (r001 to r003), 6,1,4-6. Each occurrence gives one vector of these strings, so -p 3 4 -p 6,1 gives [["3", "4"], ["6,1"]]; see JuLeAna.parse_period_runs.
  • --runs, -r: run numbers for the periods given without runs, as one vector per occurrence.
  • --runmode, --rm: local or slurm, replacing the config's run mode.
  • --dataset: name of the dataset in the metadata datasets/runlists that selects the runs; "default" when not given.
  • --log_path, -o: log directory; "" when not given.
  • --theme: name of the color theme of the interface; nothing when not given.
  • Flags, false when not given: --no-tui, --new-production, --reprocess, --only_runs (--or), --only_partitions (--op), --submit_jobs, --ignore_config, --analysis_runs_only.

Examples

julia> args = JuLeAna.parse_commandline(["-c", "config.json", "-p", "3", "4", "--reprocess"]);

julia> args["periods"], args["reprocess"], args["only_runs"]
([["3", "4"]], true, false)

JuLeAna.parse_period_runs — Function
JuLeAna.parse_period_runs(period_args, run_args)

Turn the --periods and --runs options of parse_commandline into (periods, runs). period_args and run_args are vectors with one vector per occurrence of the option: strings like "6", "6,1", "6,1-3" or "6,1,4-6" for periods, and run numbers for runs.

periods is a Vector{DataPeriod} in the given order, or nothing without --periods. runs is

  • a Dict{DataPeriod,Vector{DataRun}} with the sorted runs of each period given with runs, when any is; the other periods keep all their runs;
  • else the --runs numbers as a Vector{DataRun} for all given periods;
  • else nothing.

Throws an ArgumentError for a malformed string, a period given twice, a run range that ends before it starts, and for --runs together with periods given with runs.

Examples

julia> string.(periods), sort([string(p) => string.(r) for (p, r) in runs])
(["p03", "p06", "p07"], ["p06" => ["r001", "r002", "r003"], "p07" => ["r002", "r005"]])

JuLeAna.init_process — Function
init_process(log_path::AbstractString = "", log_level::LogLevel = Logging.Info; console::Bool = true)

Prepare the current process for processing: set the LegendSpecFits fit time limit to 180 s, install the global logger built by processing_logger, and pin the Julia threads with ThreadPinning.pinthreads(AutoThreadPinning()) of ParallelProcessingTools: to the CPUs of the affinity mask of the process if it has one, as in a SLURM job, else not at all. The pinning is logged. A process inside a SLURM job (SLURM_JOB_ID is set) whose job sets JOB_SHMTMPDIR uses that node-local shared-memory folder for tempdir().

With a non-empty log_path, the process appends its records of level log_level to its file in that directory (see process_log_file). The main process shows records of level Info and above on the terminal unless console = false; a worker shows only warnings and errors there. setup_session runs it on the head and on every worker.

JuLeAna.DataflowSession — Type
mutable struct DataflowSession

State of a dataflow session, as returned by JuLeAna.setup_session: the processing config, the LEGEND data and the selection and dependency graph that run_processing works on. A DataflowController holds the session of the terminal user interface.

Fields:

  • args::Dict{String,Any}: parsed command line options, used to reload the config.
  • l200::LegendData: the LEGEND data the session processes.
  • config::ProcessingConfig: the validated processing config.
  • periods::Vector{DataPeriod}: selected periods.
  • runs: selected runs: nothing selects all runs of each period, a Vector{DataRun} the same runs in every period, and a Dict{DataPeriod,Vector{DataRun}} the runs per period, where a period without an entry keeps all its runs.
  • run_steps::Vector{Symbol}, partition_steps::Vector{Symbol}: run and partition steps scheduled by default, sorted by rank.
  • run_status, partition_status: completion flags of the dependency graph, run_status[period][step][run]::Bool for every run step and partition_status[period][step]::Bool for every partition step of the config. A step that is not scheduled starts as true, so steps that depend on it do not wait.

DataflowSession(; args, l200, config, periods, runs=config.runs, run_steps, partition_steps, run_status, partition_status) builds a session from keywords.

JuLeAna.read_report — Function
read_report(path::AbstractString)

Read the report at path and return a NamedTuple with the fields

  • path: the given path.
  • state: :missing if there is no file at path. Otherwise the Processor Status table of the report (Success is :ok, Warning is :warning, Failure is :failed) or, if the report has none, :failed if any entry failed, else :warning if any entry has a warning, else :ok.
  • date: the DateTime of the Time of processing: or Date of processing: line, or nothing if there is no such line or it holds no ISO 8601 timestamp.
  • n_entries, n_failed, n_warnings: the number of entries, of failed entries and of entries with a warning. An entry is a row of a table with a Status column, per detector and filter type for the fit reports and per filekey for the DSP reports. An entry fails when its status cell contains Failure and has a warning when it contains Warning.
  • failures: a vector of (label, error) pairs of strings, one per failed entry. The label is the detector, the failed detectors of a DSP report (one pair per detector), or else the first cell of the row, followed by (filter or energy type, partition) when the row has such columns. The error joins the non-empty cells of the columns whose header contains Error.

An unknown value in the Processor Status table throws an ArgumentError.

JuLeAna.run_processing — Function
run_processing(cfg::ProcessingConfig, l200, periods, run_steps, partition_steps,
    run_status, partition_status; processors::AbstractDict{Symbol}=PROCESSORS,
    check_dependencies::Bool=true, reprocess::Union{Nothing,Bool}=nothing,
    processor_log_level::Union{Nothing,LogLevel}=cfg.processor_log_level,
    processor_plot_level::Union{Nothing,Symbol}=cfg.processor_plot_level,
    max_parallel_steps::Integer=cfg.max_parallel_steps, stop::Threads.Atomic{Bool}=Threads.Atomic{Bool}(false),
    abandon::Threads.Atomic{Bool}=Threads.Atomic{Bool}(false),
    progress_store::Union{Nothing,ProgressStore}=nothing,
    recorded_item_seconds::AbstractDict{Symbol,<:Real}=Dict{Symbol,Float64}(),
    recorded_item_p99::AbstractDict{Symbol,<:Real}=Dict{Symbol,Float64}())

Run the partition-level steps partition_steps for every period in periods and the run-level steps run_steps for every period and every run listed in run_status. Processor functions are looked up by name in processors. l200 (usually a LegendData) is passed to every processor and to the run-info checks is_analysis_run and is_lrun. run_status lists the runs to process: every run of a period that has an entry in the first step's table.

Each step of a period, and at run level of a run, starts as soon as the steps it waits for have finished, so steps that do not wait for each other run at the same time. A step waits for the steps that waited_processors returns for it in the processor_graph of cfg, with run_steps and partition_steps as the selected steps:

  • a run step for the same run, or, when the graph reaches it through a partition step, for all runs of the periods given by partition_periods that are in periods;
  • a run step that a partition step waits for, for all runs of the periods given by partition_periods that are in periods: a partition can contain runs of later periods;
  • a partition step for the same period.

A partition step whose processor returns true finishes only when the same step has finished for the previous period. Without check_dependencies a step waits only for the steps of its own level, for the same run or period.

Steps that are ready start, and the items they hand to parallel get free workers, in this order (see JuLeAna.waiting_chains and JuLeAna.WorkerQueue): the step with the longest chain of selected steps that wait for it first, then the one with the most selected steps that wait for it, then by rank, name, period and run. When every step runs with reprocess = true and an item time is known, the estimated time of that chain comes first: a step takes the item time of its processor times max(1, items / workers), with the number of workers in the worker pool and, for a step without counted items, one item. The item time of a processor is the cfg.item_time_estimate (median, 95th percentile or maximum) of the durations of its items of this run once cfg.item_time_minimum_items of them have finished, else recorded_item_seconds[processor] (such as the same statistic from the history of the production), else the median of the known ones. The order is updated after every finished step and before a worker is handed out when the number of workers changed. With max_parallel_steps > 0 at most that many steps run at the same time. At the start, the items of every step whose processor registers an items function (see register_processor!) are counted, except for the runs that are skipped; parallel logs a debug message when such a step hands it a different number. A step that is skipped because the run is not an analysis run (with cfg.analysis_runs_only) or not in the run info counts as finished. run_status[period][step][run] and partition_status[period][step] are set to true when a step finishes.

A processor whose keyword argument timeout is "auto" gets, when each of its steps starts, the item timeout cfg.item_timeout_factor times the 99th percentile of the durations of its items, at least cfg.item_timeout_minimum_minutes: of its items of this run once cfg.item_time_minimum_items of them have finished, else recorded_item_p99[processor] (such as the latest one in the history of the production). Without either it gets timeout = 0, no timeout. The timeout of a step does not change while it runs.

When a step throws, no further step starts, and once the running steps have ended a CompositeException of the failures is thrown. Steps that wait for each other in a circle throw an ErrorException that names them. Setting stop[] to true stops the run: no further step starts, and parallel hands no further items to workers and throws ProcessingStopped once its running items have finished. With abandon[] also true, parallel throws without waiting for its running items, which go on in the background. reprocess, when not nothing, overrides the reprocess keyword of every processor, processor_log_level, when not nothing, the log_level of every processor (a processor's log records are written at that level, see ProcessorLevelLogger), and processor_plot_level, when not nothing, the plot_level of every processor (see @debug_plot). Plots are saved in the plot_formats of cfg (see save_plot). A step without an entry in processors throws an ArgumentError before any work starts. Return nothing.

With a ProgressStore as progress_store, the store is reset to the scheduled steps, every step's state is recorded there (:skipped for a run that is not processed, :failed or :stopped for a step that threw) and parallel records the items of the step that calls it. Steps that never finished are :stopped when the run was stopped and :cancelled otherwise. The store records the durations of the items (see JuLeAna.item_timings) only when every step runs with reprocess = true.

JuLeAna.run_step — Function
run_step(step::Symbol, period, run = nothing; detectors = nothing, outputs = :temp,
    output_dir = nothing, config = JuLeAna.default_config_file(), l200 = nothing,
    show_report::Bool = isinteractive(), debug = false, pause = nothing, error_plots = nothing, log_level = nothing,
    plot_level = nothing,
    processors::AbstractDict{Symbol} = PROCESSORS, kwargs...)

Run the processor step for period and, for a run-level processor, run, in the calling Julia process, for example in the REPL. A partition-level processor takes no run. step is the name of a registered processor, a key of JuLeAna.PROCESSORS, and JuLeAna.processors lists them with their level, category and rank; ?JuLeAna.<step>, e.g. ?JuLeAna.process_energy_calibration_cal, shows what the processor does and its keywords.

Only the defaults are needed: by default, nothing is written to the data production, and the plots, reports and data files go to a temporary directory.

Keywords

  • detectors: the detectors to process, e.g. [:V01234A]; they are processed again, also when their parameters or output exist. nothing (the default) processes all detectors, with reprocess = true unless given. A detector that the processor does not process in this run or partition stops the call with an error listing the detectors it processes.
  • outputs: :temp (the default) writes the plots, reports and the data tiers the processor writes (its output_tiers, see register_processor!) to output_dir, and no parameters or validity; parameters are read from the production, and the detectors not in detectors are not run. :production writes everything to the production paths of l200, which cannot be undone; the detectors not in detectors are skipped as already processed, so the parameters, validity and reports stay complete.
  • output_dir: the directory of the temporary outputs; by default one temporary directory for all calls in the Julia session, see step.output_dir. The report of each call is appended to <output_dir>/reports/<step>.md: the report of the processor with only the rows of detectors, and below it the plots of each detector the processor saved during this call, in the order they were saved.
  • config: a ProcessingConfig or the path of a config file; by default the config of the data production. The processor must be in it; for a processor that is not, use the config of the package, joinpath(pkgdir(JuLeAna), "config", "processing_config.yaml").
  • l200: the LegendData to use; by default LegendData(:l200), built after the env_variables of config are set.
  • show_report: display the report at the end with display_report; the default in an interactive session.
  • debug: true runs the items one after the other in the calling process, without workers and timeout, and captures each failed @process_step as a Failure with the variables of the processor at that step; see JuLeAna.failure. A summary of the failures is printed at the end. :infiltrate does the same and also stops at each failed step in an Infiltrator prompt with these variables; leaving the prompt goes on with the error. Needs using Infiltrator.
  • pause: :all, or the names of steps, e.g. ["e_cusp simple calibration"], with their interpolations done: stop in an Infiltrator prompt after each of these steps that succeeds, with the variables of the processor and the value of the step as step_value. Implies debug = true if debug is false. Needs using Infiltrator.
  • error_plots: whether a failed @process_step runs its on_error hook, which saves a debug plot; nothing (the default) takes the error_plots setting of the processor in config. In the report, these plots, whose names start with error_, are linked, not embedded.
  • log_level: :debug, :info, :warn or :error: the processor logs at this level, also to the terminal; at :debug this includes the debug records of the DEBUG_LOG_PACKAGES. nothing (the default) takes the log_level of the processor in config, which applies to the log files only. Items on workers log to the workers' log files.
  • plot_level: :info or :debug; at :debug the processor also saves its @debug_plot plots, which the report shows like the others. nothing (the default) takes the plot_level of the processor in config.
  • processors: the processors by name, JuLeAna.PROCESSORS by default.
  • kwargs: keyword arguments of the processor, e.g. timeout = 0. The processor gets the keyword arguments of config, then only_first_period = false for a partition-level processor and reprocess = true when detectors is nothing, then kwargs. A timeout of "auto" becomes the item timeout from the latest 99th percentile of the item times of the processor in the history of the production l200 (see run_processing).

Workers

The items of the processor, e.g. its detectors, go to the workers of the ParallelProcessingTools worker pool, or run in the calling process when no workers are started. Workers started from the session need JuLeAna and ParallelProcessingTools in the active environment:

using JuLeAna
ParallelProcessingTools.@always_everywhere using JuLeAna
ParallelProcessingTools.runworkers(ParallelProcessingTools.OnLocalhost(n = 4))

runworkers returns at once; the workers join the pool when they are up, see ParallelProcessingTools.worker_resources().

Returns

Return a StepOutput with the report, the reports of the processor, the results of its items and the captured failures.

Throws an ArgumentError if step is not registered or not in config, if run is given for a partition-level processor or missing for a run-level one, if detectors is given for a processor that cannot select detectors, or if outputs is not :temp or :production.

Examples

using JuLeAna
# run level: a detector of p03 r000
step = run_step(:process_energy_calibration_cal, 3, 0; detectors = [:V01234A])
# partition level, no run
step = run_step(:p_process_energy_cal, 3; detectors = [:V01234A])
JuLeAna.display_report(step.report)
# capture the failed steps of a detector
step = run_step(:process_energy_calibration_cal, 3, 0; detectors = [:V01234A], debug = true)
f = JuLeAna.failure()

JuLeAna.WorkerQueue — Type
JuLeAna.WorkerQueue(order = identity, refresh = () -> false)

Order in which the waiting items of parallel get free workers. run_processing sets one queue for all steps of a run. A free worker goes to the waiting item with the smallest order(key), and among equal ones to the item that came first. The key of an item is its step in run_processing followed by the item's position, and order puts the priority of the step first, so the items of a step get workers in their order. When the priorities change, JuLeAna.resort! sorts the waiting items again; refresh() is called before every handout and returns whether they changed.

Every waiting item adds one task that takes a worker from the pool, and that task hands the worker to the item that is first at that moment. These tasks wait side by side, so the initialization of new workers, which happens when a worker is taken, also runs side by side.

struct ProcessingConfig

Validated processing settings, built from a processing config file and the command line options of the dataflow driver.

Fields:

  • runmode::Symbol: :local or :slurm.
  • submit_jobs::Bool: whether the driver starts the workers itself.
  • local_n::Int: number of local workers (config.runmode_settings.local.n).
  • local_julia_settings::Vector{String}: Julia flags for local workers.
  • slurm_flags::Vector{String}: SLURM flags for SLURM workers.
  • slurm_julia_settings::Vector{String}: Julia flags for SLURM workers.
  • slurm_worker_memory::Symbol: :shared, the SLURM workers of a job share its memory, or :fixed, each worker gets the job's memory per node divided by its workers per node.
  • env_variables::Dict{String,String}: environment variables for the driver and workers.
  • periods::Union{Nothing,Vector{DataPeriod}}: selected periods; nothing selects all.
  • runs::Union{Nothing,Vector{DataRun}}: selected runs; nothing selects all.
  • analysis_runs_only::Bool: process only runs marked as analysis runs.
  • only_partitions::Bool: process only partition-level processors.
  • only_runs::Bool: process only run-level processors.

  • worker_restart_delay_seconds::Int: seconds a worker slot of a start script waits before it starts a new worker in place of one that ended.
  • worker_heartbeat_timeout_minutes::Int: minutes after which a start script takes the interface as gone if it has not touched its heartbeat file, and ends its allocation.

  • item_time_minimum_items::Int: number of done items of a processor in the current processing run from which their durations replace the recorded ones, for the estimates and the item timeouts. Fewer items give an unreliable statistic, and the first items of a run include the compilation.
  • item_timeout_factor::Float64: a processor with the keyword argument timeout = "auto" gets this factor times the 99th percentile of its item durations as item timeout (see run_processing).

JuLeAna.parallel — Function
parallel(f, iterator::AbstractArray, log_nt; timeout::Real=0, retry::Bool=false, process_name::AbstractString="")
parallel(iterator::AbstractArray, log_nt; kwargs...) do itr
    ...
end

Apply f to every element of iterator on the ParallelProcessingTools worker pool and return an array of itr => f(itr) pairs with the same shape and axes as iterator. The function comes first, as in map, so a do-block can supply it. Inside run_processing with a ProgressStore, each item's start, worker and outcome are recorded for the current step; otherwise a progress bar labeled process_name shows the finished items.

log_nt is the NamedTuple type of the processor's report rows. On success f returns a NamedTuple with at least the fields processed::Bool and log, a row of type log_nt (or a Dict of such rows), so that successful and failed items have the same shape for master_status and the report. An item whose result has skipped = true, which partition steps return for a detector left to the step of an earlier period, counts as not run in the progress.

An item whose f throws, or exceeds timeout seconds when timeout > 0, does not abort the batch: its pair is itr => (processed = false, log = failure_log(log_nt, itr, msg)). When an item exceeds timeout on a worker, the process of that worker is ended at once with JuLeAna.kill_worker, also while it computes; a worker started by a start script of JuLeAna.worker_start_script is then replaced. An item on the main process has no timeout. An item whose worker process ends while it runs, after the timeout or otherwise (such as for lack of memory), fails; with retry = true it is tried again on another worker, up to three times in all. A worker that ends with its SLURM job, at the job's time limit or cancelled (see JuLeAna.worker_job_ended), does not count: the item runs again on the next free worker, waiting for one if none is left, and fails after three such ends. An error thrown by f is not retried.

Element types without a failure_log method for log_nt are rejected with an ArgumentError before any work starts.

Inside run_step, f sees the detector selection of run_step also on the workers (see redo_detector); with outputs = :temp, items whose detector is not selected are not run and are missing from the result. For items with a detector field, parallel throws an ArgumentError before any work starts if a chosen detector is not among them.

Inside run_step with debug = true, the items run one after the other in the calling task, without workers and without timeout.

Inside run_processing, a stop of the processing run takes effect here: items that have not been handed to a worker are not run, items already running finish, and parallel then throws ProcessingStopped instead of returning. When the run is stopped without waiting for running items, parallel throws right away and the running items go on in the background; their workers return to the pool when the items end. The items of all running steps get free workers in the order of the run's JuLeAna.WorkerQueue.

Examples

using LegendDataManagement: FileKey, ProcessStatus
Row = NamedTuple{(:Filekey, :Status, :Events, :Error)}
filekeys = [FileKey("l200-p03-r000-cal-20230311T235840Z")]
results = parallel(filekeys, Row; process_name = "count events") do fk
    (processed = true, log = Row((fk, ProcessStatus(1), 1000, "")))
end
master_status(results)  # process_succeeded

JuLeAna.failure_log — Function
failure_log(log_nt, itr, message::AbstractString)

Build the report row for an item of parallel that threw. log_nt is the processor's NamedTuple{names} row type and message the truncated error text. The status column is ProcessStatus(0) and every column without data is filled with "-".
